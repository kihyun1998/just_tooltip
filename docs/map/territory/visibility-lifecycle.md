# Visibility lifecycle

## What it is

Owns intent (`_isShowing`) and reconciles it with render state (`AnimationController.status`):
showing and hiding the `OverlayPortal`, starting and reversing the animation, the reverse-catch,
and teardown on deactivate/dispose. Vocabulary: [Intent vs Render State](../../../GLOSSARY.md#intent-vs-render-state).

## Governing decisions

- [ADR-0001](../../adr/0001-scheduler-separates-intent-from-render-state.md) — intent and render state stay two facts; the reverse-catch stays in the State. Not to be re-litigated.
- [ADR-0005](../../adr/0005-the-tooltip-draws-through-an-overlay-portal.md) — the tooltip is an `OverlayPortal`'s overlay child, built in the State's context.
- [ADR-0011](../../adr/0011-a-covered-tooltip-hides.md) — a covered tooltip hides and does not show; a covered fade its stopped tickers hold is ended at once (maintainer, 2026-11-08), and since #104 any fade-out they hold (maintainer, 2026-11-17).

## Design model

From ADR-0001, confirmed in source:

- `_show` is the only path that opens: refuses without content or while [Covered](../../../GLOSSARY.md#covered), sets `_isShowing`, freezes the anchor, lists the tooltip for Escape, shows the `OverlayPortalController`, `forward()`s, schedules `onShow` and the announcement for after the frame, and registers with the registry last (dismissing the tooltip that held the place). A fresh open first rewinds the animation to hidden (`_rewindAnimation`).
- **Registering comes last in `_show`** (#118). `TooltipRegistry.show` calls the previous holder's `dismissTooltip` synchronously; with a zero `animationDuration` that holder's fade reaches `dismissed` inside `reverse()` and its `onHide` runs there, inside this `_show`. When it registered before the overlay and `forward()`, an `onHide` that showed a third tooltip in the same registry evicted this one while its animation still sat at `dismissed`: `_hide`'s `reverse()` changed no status, so nothing ended the show, `_show` then ran `forward()`, and two tooltips were shown in one registry, the registry tracking only the third (measured on b3ef97d: B, C, D in one registry, D zero fade with `onHide: () => b.show()`, `d.show(); c.show()` left B and C shown; a later show elsewhere in the registry dismissed only B). Now the evicting tooltip's show is complete when foreign code runs, so the third tooltip's show evicts it like any shown tooltip and takes the place: the last show wins (`[D show, D hide, B show]`, C never reports `onShow`). The same order fixed three neighbours, each measured red with the old order (#118's lens): a `c.show()` turning back C's eviction fade, whose `forward()` came after the registry call and revived C after B's eviction; that `onHide` calling `c.hide()`, which was lost the same way and left C shown; and that `onHide` calling `d.show()`, which left C and D shown. Pinned in `test/just_tooltip_eviction_test.dart` (group *the onHide of a tooltip whose fade ends at once as it is evicted acts on the evicting tooltip as on any shown one*: the show, the turned-back fade — where C then fades out over frames — the hide, and D's own show; all four red with the old order). A tooltip evicted in the same call as its own show is at `0.0`, so its `reverse()` ends at once whatever its `animationDuration`; only the turned-back case fades over frames. Deferring the dismissal to a microtask instead (as `_syncRegistry`'s `take` does) was measured and rejected: in `d.show(); a.hide();` the close then lands before the eviction and is settled as a dismissal, which reddened *during the fade the eviction began, and turned back by its controller, shows again when a later eviction ends*. The zero-fade `onHide` still runs synchronously inside the evicting `show()` call, once (implementer's derivation; [a-show-is-set-before-the-registry-runs-another-tooltip](../invariant/a-show-is-set-before-the-registry-runs-another-tooltip.md)).
- `_hide` only `reverse()`s. The overlay is hidden when the animation reaches `dismissed` (`_onAnimationStatus`), which ends the show through `_endShow` and calls `onHide` through `_callOnHide`.
- **`onShow` reports a drawn tooltip; `onHide` answers it** (#103). The post-frame `onShow` runs only if the State is mounted, still `_isShowing`, and `_showGeneration` has not moved — a show hidden, removed, or ended and begun again in that frame reports nothing, or once. `_announcedShow` records that it ran; `onHide` is called only then. Before #103 `onShow` ran inside `_show`, so a tooltip removed in the frame its show began (a tap whose own callback removes the content, flutter_folderview#182) reported `onShow` and never `onHide`, `_hideImmediate` calling none. `_callOnHide` waits for the frame when the hide ends in a build: a content-loss hide whose fade had nothing left reached `dismissed` inside `didUpdateWidget` (measured, #103). A tooltip moved by a `GlobalKey` while fading out loses its `onHide`: `_hideImmediate` clears `_announcedShow` and the fade stops with the teardown (#109) — before #103 it ran on and reported `onHide`; kept unreported, as a tooltip leaving the tree calls no `onHide` (maintainer, 2026-11-08). While the app is in the background no frame comes, so `onShow` waits for frames to resume (read in `scheduler/binding.dart`, not run). See [a-callback-never-runs-in-a-build](../invariant/a-callback-never-runs-in-a-build.md).
- **The reverse-catch is in `_show`**, for the scheduler's requests and the controller's alike (#101): a tooltip `_fadingOut` (shown, animation reversing) passes the same content and Covered gates, takes the registry back (leaving its evicted set), re-tracks for Escape, resets `_sawVisibleTarget` and `forward()`s — without showing the portal again, re-freezing the anchor, announcing or calling `onShow` (no `onHide` was called). Before #101 the catch sat in the scheduler's handler, and `showTooltip` returned on `_isShowing`, which stays true through the reverse. Resetting `_sawVisibleTarget` matters for a child scrolled out of sight: a caught tooltip that kept it `true` was hidden again by the next layout, while a `controller.show()` after the fade waits at the clip edge (#101's review; pinned in `test/just_tooltip_fading_test.dart`; since #130 a trigger does not show a tooltip on a child clipped away entirely). Keeping the anchor keeps a tooltip that never left the screen where it is.
- `_hideImmediate` (deactivate, dispose) tears down without animation, ending the show through `_endShow` as the fade does. It drops show intent through `_dropShowIntent`, settling a close that was fading out, and leaves the trigger facts and the dismissal's holds (`_pointerHold`, `_focusHold`), so a tooltip moved by a `GlobalKey` with the pointer still on its child or focus still inside is shown again by its `activate` reconcile, and one dismissed stays closed ([show-intent](show-intent.md), #122). `deactivate` also `stop()`s the animation, and the next fresh `_show` rewinds it to `0.0` (#109): before, a tooltip moved by a `GlobalKey` started its next show where the old one had been — opacity `1.0` on the first frame, or `0.75` mid-fade — and a running fade ran on after the teardown. Two traps, both measured: setting `value = 0.0` inside `deactivate` notifies the value listeners during the build, so the overlay's transition (a `SlideTransition` being torn down) failed "setState() called during build"; and the rewind detaches the status listener, because the `dismissed` it reports would reach `_onAnimationStatus` after a hover or focus show had set `_showIntent`, drop it and mark the tooltip dismissed, so the tooltip opened and then stayed when the pointer left (#109's review). `stop()` notifies nothing; a stopped controller keeps its `reverse` status, which `_fadingOut` ignores since `_isShowing` is false. `deactivate` also detaches the controller, and `activate` attaches it again ([programmatic-control](programmatic-control.md), #102).
- A covered hide (`_syncCovered`) calls `_hide` from a post-frame callback: the route's notice arrives during a build, and a fade with nothing left to animate reaches `dismissed` inside `reverse()`, which ran `onHide` inside the build (measured by #100's lens read). Under an opaque route the tooltip's tickers stop once the route below goes offstage, about 500 ms after the push in a widget test; a fade still running then holds `onHide` until the pop. `_endHeldFadeAfterFrame` sets the value to `0.0` after the frame when the tickers have stopped mid-fade, covered or not; `_hide` does it at once when they were already stopped (#104). Either way the show ends as a zero-length fade ends; see [a-muted-ticker-holds-a-fade](../invariant/a-muted-ticker-holds-a-fade.md).
- A tooltip whose own route is popped gets no notice from a plain pop (`ModalRoute.didPop` calls `changedInternalState` only for a local-history entry), so `deactivate` takes it as before; a replacement does notify (ADR-0011).
- `_hideOverlay` hides the portal. `OverlayPortalController.hide()` asserts during build and layout (`SchedulerPhase.persistentCallbacks`) — where `deactivate` runs, and where `didUpdateWidget` can reverse an animation already at `0.0` — so there it waits for a post-frame callback and skips the hide if `_isShowing` is true again. It also skips a controller that is not showing: a detached, hidden controller asserts on `hide()` (Flutter 3.13 `widgets/overlay.dart`). Measured: before the deferral, 82 of 200 tests failed on the `deactivate` assertion.
- A `forward()` can cover a `reverse()` that has not left `0.0`, so "the tooltip is visible" proves nothing about whether a hide happened; #39's tracking bug passed `findsOneWidget` this way and surfaced only when the test asserted `onHide` was *not* called (`docs/agents/lessons.md`, Step 5).

- **A show ends in `_endShow`**, from both teardown paths (#111): it clears `_isShowing`, `_sawVisibleTarget`, `_frozenAnchor`, `_resolvedDirection` and `_arrowCenterOffset`, leaves the registry, `_shown` and `_pending`, and hides the overlay; leaving the registry revives the tooltips it evicted when this one held the place ([show-intent](show-intent.md), Eviction; [tooltip-registry](tooltip-registry.md)). What differs stays at the callers: the fade path drops `_showIntent` into `_dismissed` and calls `onHide`; `_hideImmediate` resets the scheduler and `_announcedShow` and drops `_showIntent` through `_dropShowIntent`, calling no `onHide`; it leaves `_pointerInside` and `_dismissed` (#122). Before #111 the two paths cleared the per-show fields by hand and only the fade revived, so a tooltip that left the tree while shown left the one it evicted hidden, its trigger still inside. See [a-show-ends-in-one-place](../invariant/a-show-ends-in-one-place.md).

## Reference behaviour

- Flutter 3.41.9 `widgets/raw_tooltip.dart` — `OverlayPortal.overlayChildLayoutBuilder` (3.32+) with an `OverlayPortalController`, shown when the animation leaves `dismissed` and hidden when it reaches it. This package uses it too since ADR-0008 (floor 3.32); ADR-0005 had kept the plain `OverlayPortal` for the 3.13 floor.

## Blast radius

- [tooltip-registry](tooltip-registry.md) — `_show` registers and `_endShow`, where both teardown paths end, unregisters; a missed `remove` leaves a dismissed tooltip registered.
- [target-tracking](target-tracking.md) — the target is resolved while the `OverlayPortalController` shows the overlay child; a clipped-away child is hidden through `_hide` after the frame.
- [transitions](transitions.md) — the animation this territory drives is what transitions read.
- [content](content.md) — `_show`'s content guard is one of content's three gates.
- [semantic-tooltip](semantic-tooltip.md) — `_show` schedules the announcement with `onShow`.
- [show-intent](show-intent.md) — `_show` lists the tooltip for Escape; `_endShow` unlists it, and its registry `remove` revives the evicted tooltips.
- [public-surface](public-surface.md) — `onShow` / `onHide` are the only way consumers observe visibility (ADR-0002).
