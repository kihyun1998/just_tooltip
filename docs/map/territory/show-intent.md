# Show intent

## What it is

Turns the trigger edges on the child — `MouseRegion` enter/exit, focus moving — into one derived
boolean, and hands only its transitions to the scheduler; and dismisses a shown tooltip on
Escape. It is the first link of the [visibility chain](visibility-chain.md). Called hover intent
until ADR-0010. Vocabulary: [Show Intent](../../../GLOSSARY.md#show-intent),
[Dismissal](../../../GLOSSARY.md#dismissal).

## Governing decisions

- [ADR-0003](../../adr/0003-nesting-suppression-gates-a-derived-hover-intent.md) — introduces the pointer-facts layer and the microtask coalescing.
- [ADR-0004](../../adr/0004-content-gates-showing-suppressing-and-hiding.md) — adds `hasContent` as the fourth term.
- [ADR-0011](../../adr/0011-a-covered-tooltip-hides.md) — adds [Covered](../../../GLOSSARY.md#covered) as a gate; a covered hide is not a dismissal (maintainer, 2026-11-08).
- [ADR-0010](../../adr/0010-a-keyboard-user-can-show-and-dismiss-a-tooltip.md) — adds the keyboard-focus fact (`enableFocus`, opt-in; key-arrived focus only; the pointer wins; an evicted tooltip comes back) and dismissal on Escape; WCAG 2.1 SC 1.4.13 is the yardstick (maintainer, 2026-10-26).
- [ADR-0010, amended by #116](../../adr/0010-a-keyboard-user-can-show-and-dismiss-a-tooltip.md) — before its revival an evicted tooltip gains show intent only on a new trigger act; every other re-derivation waits (maintainer, 2026-11-12).
- [ADR-0012](../../adr/0012-wait-duration-delays-only-a-hidden-tooltip.md) — a trigger returning while the tooltip is shown or fading out skips `waitDuration` (maintainer, 2026-11-12).
- [ADR-0012, amended 2026-11-16](../../adr/0012-wait-duration-delays-only-a-hidden-tooltip.md#amendment--2026-11-16-the-body-of-an-interactive-tooltip-holds-it-as-its-child-does) — the body of an interactive tooltip holds it as its child does: the pointer entering it during a fade-out does what entering the child would (maintainer, 2026-11-16, #134).

## Design model

From the records, confirmed in source:

- `wants = _triggerInside && !_suppressed && _hasContent && !_dismissed && !_covered && !_childClippedAway && !waiting` (`_reconcileShowIntent`), where `waiting = !_showIntent && !act && _registry.isEvicted(this)` (below, *New trigger act*) and `_triggerInside = (enableHover && _pointerInside) || (enableFocus && _keyboardFocusInside)`; `if (wants == _showIntent) return` — only transitions reach the scheduler.
- **The body pointer is not a term** (maintainer, 2026-11-17, #149, chosen over making it one, which would reach suppression, eviction and revival, and dismissal). Show intent drops when keyboard focus leaves under a pointer resting on the body; the tooltip stays shown because `_reconcileShowIntent` passes `onChildExit` a `hoverOnBody` that withholds the bridge ([visibility-scheduling](visibility-scheduling.md)). Before #149 that drop hid it after the bridge, under the pointer.
- **The focus fact.** `_holdsFocus` walks `FocusManager.primaryFocus.context`'s ancestors up to this State's element, so focus in the child *or* in the tooltip's content counts (the overlay child sits in the tooltip's element subtree, ADR-0005). No widget is put around the child: a first cut wrapped it in a `Focus`, and #92's review measured that `Focus.of(context)` inside every consumer's child then returned the tooltip's node instead of theirs, `enableFocus` or not. `_onFocusChanged` (a `FocusManager` listener, only while `enableFocus`) sets `_keyboardFocusInside` when focus arrives inside while one of `_traversalKeys` (Tab, the arrow keys) is in `HardwareKeyboard.logicalKeysPressed` — a Tab is still down when the traversal it triggered lands, a focus change is applied in a microtask before the key-up — and keeps it while focus moves about inside. Any pressed key was not enough (#92's second review, measured): a Shift-click counted, and so did the focus a dialog closed by Escape gives back a frame later while Escape is still down. `highlightMode` was the first choice and was dropped: a desktop mouse click leaves it `traditional` (measured).
- **Suppression has two kinds.** `_syncSuppression` claims ancestors in `_suppressors` for the pointer and in `_focusSuppressors` for keyboard focus; `_suppressed` counts a focus suppressor only while the pointer is not inside this tooltip's child, so a pointer hovering an outer child elsewhere wins (ADR-0010). A pointer resting on the body, entered with `enableHover` on, counts as the pointer here too (#156; [nesting-suppression](nesting-suppression.md)). A dismissed tooltip keeps suppressing: its outer one does not pop up in its place.
- **Eviction.** An evicted tooltip comes back only once no tooltip in its own registry holds the place (ADR-0010 as amended by #113; maintainer, 2026-11-11). The record lives in the [registry](tooltip-registry.md): `TooltipRegistry.show` moves the tooltip holding the place into its evicted set and calls its `dismissTooltip`, which drops `_showIntent` and hides — landing during a fade-out that a close with show intent still set began (a tap, the auto-hide, a controller), it first settles that close, since it drops show intent through `_dropShowIntent`, so the tooltip is marked dismissed while its trigger is inside (below, *A close outlasts what drops show intent during its fade*); when the holder's show ends — its fade reaches `dismissed`, or it leaves the tree while shown or fading out — `_endShow`'s `remove` finds it holding the place and calls `reviveTooltip` on every evicted one, which reconciles it, so a trigger still inside shows it again (#111 put both paths through `_endShow`) — unless the eviction settled a close, where it stays closed until its trigger leaves and returns (#117). Before #117 `dismissTooltip` dropped show intent without settling, `_onAnimationStatus` then found none at `dismissed`, and the revival showed the tooltip again with the pointer never moving (measured on ddae36c for the auto-hide, a `TooltipTap.claim` tap and `controller.hide()`; pinned in `test/just_tooltip_eviction_test.dart`, group *a tooltip closed by something other than its trigger leaving …*, all red there). A fade begun by the trigger leaving, by suppression, by covering or by lost content has dropped show intent already ([content](content.md)), so an eviction during it settles nothing: the guard group *a tooltip evicted during a fade that was not a dismissal* pins all four, and only its suppression and lost-content cases go red when `dismissTooltip` sets `_dismissed` whatever show intent is (mutation) — in the other two the trigger is already outside when the eviction lands; dropping the `_fadingOut` condition reddens 25 tests, since a shown tooltip evicted outright must come back. In a chain — A hover-shown, D's `show()` evicts A, B's `show()` evicts D — A comes back when B hides, not when D's fade ends; a show ending in another registry revives nothing (both pinned in `test/just_tooltip_eviction_test.dart`, red on efd4042 where one app-wide set was re-derived by any show ending). A tooltip fading out because it was evicted does not hold the place, so when the holder leaves the tree during that fade the evicted one turns its fade back and calls no second `onShow` (pinned in `test/just_tooltip_teardown_test.dart`). A tooltip torn down while not holding the place revives nothing: with that guard removed, removing a tooltip that never showed brought A back over the B that evicted it, and A dismissed B (measured by mutation, #111 and again here). The evicted one's own hide does not clear its entry; `dispose` drops it (`forget`). A show that turns back its fade — a hover or a `controller.show()` — takes the registry back and leaves the evicted set, dismissing the tooltip that evicted it (#101; for a hover, maintainer, 2026-11-08 — before, both stayed shown). A tooltip whose registry changes moves at once (#114; maintainer, 2026-11-11): leaving a registry where it held the place revives the tooltips it evicted there, and an evicted tooltip waits in its new registry. `reviveTooltip` reconciles in a microtask, and only if by then no other tooltip holds the place in the tooltip's registry; otherwise it waits again ([tooltip-registry](tooltip-registry.md)).
- **New trigger act** (ADR-0010 as amended by #116; maintainer, 2026-11-12). Until the revival, the evicted tooltip's own re-derivations do not show it: `waiting` holds while the registry still records it (`isEvicted`), unless the reconcile carries a new act or show intent is already set. Before #116 they did: content regained, a `GlobalKey` move with focus inside and a nested release each found the trigger inside, `_show` ran, `_registry.show` took the place and dismissed the holder (measured on 78a9c21). `_pointerAct` and `_focusAct` are set by the act-producing edges and read and cleared at the top of `_reconcileShowIntent`, where each counts only while its trigger is still inside (`enableHover && _pointerInside`, `enableFocus && _keyboardFocusInside`); a reconcile coalesced from an act and other changes counts as an act. The edges: the child's `onEnter` when `_pointerMoved` (`_pointerAct`); `_onFocusChanged` when key-arrived focus begins (`_focusAct`); and a descendant's release passed `moved: true` — from its `onExit` when `_pointerMoved`, and from its `_onFocusChanged` — which `_claimAncestors` turns into the ancestor's act of the released kind only when the ancestor was `_suppressed` before the release. So the pointer going from a nested tooltip straight out of the outer one, or focus leaving a nested tooltip whose suppression the pointer on the outer one overrode, is not an act; the first cut counted every moved release, and the review and the completeness read measured an evicted A held by focus coming back over its holder that way (pinned). A tap and `controller.show()` call `_show` directly and never pass the gate. What waits: content (`didUpdateWidget`), `enableHover`/`enableFocus` changes, `activate` (a move during the act's wait is not one of these: the act's show intent survives it, below), uncovering (`_syncCovered`), and a release from `_releaseAncestors` (the descendant leaving the tree or moving) or from the descendant's own `didUpdateWidget`. `_pointerMoved` is `schedulerPhase != postFrameCallbacks`: `MouseTracker` reports an edge in two ways, with a pointer event (`updateWithEvent`) and after a frame for the tree changing under a resting pointer (`updateAllDevices`, from `RendererBinding._scheduleMouseTrackerUpdate`, read in Flutter 3.47.1). A region mounted under a resting pointer gets `onEnter` that way, and a child shifted from under it `onExit` (both measured by probe), so `enableHover` turned on and a dialog popped over the child are not acts; that cut, the reading of a release as an act, the claim-is-not-an-act rule and keeping an act's show intent through `waitDuration` are the implementer's derivations (ADR-0010). The `!_showIntent` term matters only during `waitDuration`: without it, a configuration change during the wait dropped the act's show intent and the tooltip never showed (mutation, pinned). A `GlobalKey` move during that wait keeps it too (ADR-0010 as amended by #139; maintainer, 2026-11-17): `deactivate` ends only a running show (`if (_isShowing) _hideImmediate()`), so the scheduler's timer, show intent and the pending mark of a waiting show run on, `activate`'s reconcile finds show intent set and changes nothing, and the tooltip shows when the act's wait ends, over the holder. Before, the teardown dropped show intent and cancelled the wait, and the evicted tooltip waited for its revival (`[A show, D show, A hide]` on b3ef97d). The wait runs on rather than restarting, for a tooltip that is not evicted too, and a move that also changes registry shows over the new registry's holder, as the change without a move does (implementer's derivations). A hidden tooltip keeps its other scheduler timers too, so a left-over auto-hide still closes an evicted tooltip or a revival's wait as it would unmoved (maintainer, 2026-11-18, asked in #139's run). Pinned in `test/just_tooltip_eviction_test.dart` (the pointer and the keyboard-focus act, and group *a GlobalKey move ends only the show …*), `test/just_tooltip_wait_test.dart` and `test/just_tooltip_registry_change_test.dart`, each red on dfb29f5. The record needs no field in the State, because the registry already keeps it for exactly as long as the tooltip waits. Pinned in `test/just_tooltip_eviction_test.dart` (group *before its revival …*): every wait case red on 78a9c21, every act case green there and after.
- **Focus outlasts the hover policy.** Leaving the body does not arm the [Hover Bridge](../../../GLOSSARY.md#hover-bridge) while keyboard focus holds the tooltip (unless `showDuration` owns hiding): the bridge hides without asking show intent, and a mouse crossing a focus-shown body hid it while focus stayed (measured). "Holds" is `_heldOpenByFocus`, the gates of `wants` but eviction and the clip with the pointer counted outside the child — not focus being inside: a nested tooltip holding focus suppresses this one (ADR-0010), so focus can be inside a tooltip it does not hold. The body's `onExit` first read focus inside, and once #134 let the body turn a fade back this left a tooltip shown for good: A (`enableFocus`) with nested B holding focus, the pointer on A's child (A shows, B is evicted), then on A's body (A's fade, begun when the pointer left the child and B's focus suppressed it again, turns back), then away — A stayed and B never came back, `[show B, show A, hide B]`, where d844258 hid A and revived B (measured on ada5e3e and 2cf511b; pinned in `test/just_tooltip_body_test.dart`, group *the pointer leaving the body*, red with the old guard; removing the guard reddens the two focus-holds-the-body tests). `_showIntent` in its place was wrong on 8893217: a fade the body turned back kept show intent `false` there, so an eviction fade of a focus-shown tooltip turned back from the body hid on leaving the body with focus still holding it (measured; pinned in the same group, red with `_showIntent` as the guard on 8893217). Since the turn-back re-derives show intent (below, *The body turns a fade back*), `_showIntent` as the guard passes every test and every row of the closers matrix too (measured); `_heldOpenByFocus` stays, reading focus rather than what was derived from it. The derivation counts the pointer outside the child — the opaque body region hides the child's region beneath it, so the pointer on the body is never inside the child — and off the body, which since #156 counts against a focus suppressor (`pointerOnBody`, [nesting-suppression](nesting-suppression.md)). It also reads the focus hold of a dismissal (implementer's derivation under the maintainer's wording; not shown to the maintainer): a tooltip closed with Escape while focus was inside, then shown by `controller.show()`, hides once the pointer has crossed its body and left, as one with no focus inside does, where the old guard kept it shown, `[show, hide, show]` (measured on 2cf511b by this change's review; pinned in the same group, red with the old guard and with the guard reading only focus inside and no focus suppressor). Focus there holds the tooltip closed, not open. When the tooltip reaches `dismissed` by any path other than its trigger leaving — a tap, the auto-hide, a controller — with `_showIntent` still set, `_onAnimationStatus` settles the close: `_settleClose` drops it and marks the tooltip dismissed for each trigger inside (`_markDismissed`), so the state says what the screen shows and the tooltip waits for its trigger to return. No hover show is waiting out `waitDuration` by then: a returning trigger skips the wait while the tooltip is shown, and a controller show cancels one already waiting ([every-show-cancels-the-hover-timers](../invariant/every-show-cancels-the-hover-timers.md)). Before #106 one could be, and when it fired it opened the tooltip with no show intent, which the trigger leaving did not hide.
- **A close outlasts what drops show intent during its fade** (#126; implementer's derivation). The inference above runs at `dismissed`, so whatever drops show intent earlier in the fade erases its evidence. Every site that drops show intent therefore goes through `_dropShowIntent`, which settles first when the tooltip is fading out: the reconcile's transition to `false` (suppression, the trigger leaving, covering), the content-loss hide in `didUpdateWidget`, `_syncCovered` and `dismissTooltip` ([show-intent-drops-after-settling-a-fading-close](../invariant/show-intent-drops-after-settling-a-fading-close.md)). Show intent still set during a fade means the fade began with a hide that did not drop it: a tap, the auto-hide, a controller (`hide()`, `toggle()`). The clip-away hide was one too until #130: it kept show intent, so the settle at `dismissed` treated it as a close (a focus-shown tooltip scrolled out of sight and back stayed closed, during the fade or after it, on 66960f7 to 4f3db24; measured by #126's lens and #130's triage). The trigger leaving, suppression, content loss, covering, the clip-away hide (`_hideClippedAway`, below) and an eviction while shown drop show intent before their hide, so the settle never marks them. `_dismissByUser` sets `_dismissed` itself, and `_hideImmediate`, the teardown, drops show intent through `_dropShowIntent` and keeps `_dismissed` (#122). Measured on 66960f7 with the second event 60 ms into a 200 ms fade, against the same event after the fade: a tap-closed tooltip whose pointer moves onto a nested tooltip and back came back (closed after the fade); its content going and returning brought it back (closed after the fade); a `controller.hide()`-closed, focus-shown tooltip covered by a page (`requestFocus: false`) and uncovered came back (closed after the fade). All three now match the after-fade result; pinned in `test/just_tooltip_dismissal_test.dart`, each red on 66960f7 and with its site's drop made plain (mutation); settling without the `_fadingOut` condition reddens 34 tests. Content loss and covering that *start* a fade are still not dismissals (ADR-0004, ADR-0011): the drop comes before their hide, so there is nothing fading to settle. Recording the dismissal when the close starts instead was not taken: show intent would then be gone for the whole fade, so a reconcile during it (a configuration change, a nested release) would arm the Hover Bridge, and a fade turned back by `controller.show()` (#101) would have to restore both show intent and the `_dismissed` from before the close.
  The eviction drops show intent while the tooltip still wants to show, so a close during the eviction's fade finds nothing to settle: `d.show(); a.hide();` brought A back when D hid, where `a.hide(); d.show();` kept it closed (measured on 66960f7). `_closeOnRequest` — `hideTooltip` and the scheduler's `onClose` (a tap on a shown tooltip, the auto-hide) — therefore gives show intent back to a tooltip fading out, `isEvicted` and `_openToShow` — the gates of `wants` but the eviction — and the settle at `dismissed` marks it (#126 for `hideTooltip`; #129 put the tap and the auto-hide through it). Once the eviction's fade has ended there is no settle left to read it, so the same condition on a hidden tooltip with no show intent — one waiting for its revival — sets `_dismissed` at once: an explicit close of an evicted tooltip cancels its revival whenever it lands (ADR-0010 as amended by #129; maintainer, 2026-11-12). Measured on dd1dc7d, A hover-shown, evicted by D's `show()`, then `d.hide()`: `a.hide()` after the fade, a `TooltipTap.claim` tap 60 ms into it, and the auto-hide during or after it each brought A back; pinned in `test/just_tooltip_eviction_test.dart` (groups *a tooltip its controller hides after another one evicted it* and *a tooltip a tap or its auto-hide closes after another one evicted it*), six red on dd1dc7d. Setting `_dismissed` directly is safe there and not during the fade, the direction rejected below: a hidden tooltip has no fade for `show()` to turn back, and `a.show()` after it keeps `_dismissed` just as it does after `a.hide()` with no eviction once the fade has ended. The `!_showIntent` condition keeps out an evicted tooltip a new trigger act is already showing, still waiting out `waitDuration`: its wait timer shows it regardless, and the first cut left it shown with `_dismissed` set, so the next re-derivation (a setting turned on) hid it with the trigger still inside (measured by #129's review and lens). Since #136 a `controller.hide()` there cancels the wait in `hideTooltip` before reaching this branch, so the condition guards only the auto-hide left over from an earlier show; pinned by *an auto-hide left over from an earlier show …* in `test/just_tooltip_wait_test.dart`, red without the condition (its effect shows only once `showDuration` is gone, since with it set the re-derivation's `onChildExit` hides nothing). The trigger leaving and the Hover Bridge reach the scheduler's `onHide`, which is `_hide` alone: the first cut sent them through `_closeOnRequest` too, and #129's review measured the bridge running out after A's child slid back under a resting pointer (an edge after a frame, not an act, so the reconcile leaves the bridge armed) marking an evicted A dismissed, where dd1dc7d showed it on the revival (pinned, red with the bridge routed through `_closeOnRequest`). An evicted tooltip is shown and not fading out only between `_syncRegistry`'s `take` and the microtask that dismisses it; everywhere else `TooltipRegistry.show` dismisses it in the call that records it and every show takes it out of the set, so a tap on one is a close during the fade or, once it is hidden, a show (a new trigger act, #116), and `toggle()` shows it (#101). Inside that window a close of a hover-shown tooltip has show intent and settles as any close does (read, not run; #129's lens). The registry empties its evicted set before the revival's microtask, so between a holder's show ending and that reconcile the tooltip is neither evicted nor shown; `reviveTooltip` sets `_revivalPending`, cleared by the next reconcile or, when `keepsWaiting` turns the revival back, by that branch (the tooltip is recorded as evicted again, so `isEvicted` covers it from there), and `_closeOnRequest` counts it as waiting. Without it a `hide()` from the holder's own `onHide` (called synchronously at its fade's end), or right after a holder with a zero-length fade hid, still let the revival show the tooltip (measured by #129's re-review on the repaired cut; pinned in `test/just_tooltip_eviction_test.dart`, group *… before the revival runs, stays closed*, red without the flag). Leaving the flag set after the reconcile survives every test, for the same reason as the `isEvicted` mutation below (measured again with #159's tests): once reconciled, a tooltip that is not evicted has `_showIntent == _openToShow`. A turned-back revival is not reconciled, and a show that takes the place back (`controller.show()`, a tap) takes the tooltip out of the evicted set without one, so there the two differ. Before #159 the turned-back branch left the flag set, and the tooltip, once shown that way, still counted as waiting for its revival: A hover-shown, evicted by D's `show()`, D's `onHide` showing B, then `a.show()`, `a.hide()` with the pointer resting, and A's content going and coming back — A stayed closed, where with B shown after the revival had reconciled it showed again (measured on 19302d6). Pinned in `test/just_tooltip_eviction_test.dart`, group *a tooltip that shows after a revival the registry turned back …*, for `controller.show()` and a `TooltipTap.claim` tap, both red without the clear. Clearing the flag in `_show` instead fixes that case too, but a `show()` and `hide()` between the holder's show ending and the revival's microtask then left the revival to show the tooltip again (pinned beside the onHide cases in the group *… before the revival runs, stays closed*, red with the clear moved to `_show`): there the revival has not run, and the flag is what still marks it as pending. Which of the two a show inside the gap counts as is the implementer's derivation under ADR-0010 as amended by #129 (derivation (3): a close cancels a revival only when the revival would otherwise show the tooltip, and there it would); not shown to the maintainer. The auto-hide after the fade, `toggle()` and the trigger-leaving cases are the implementer's derivations under the call (ADR-0010). #126's first cut set `_dismissed` during the fade instead, and #126's review measured two costs: a fade turned back by `a.show()` kept that `_dismissed`, so a later eviction's revival left A closed (A shown on 66960f7, and without the first eviction); and a `hide()` landing on a tooltip that suppression had already taken out of wanting, then evicted, kept it closed when the pointer moved back (A shown on 66960f7). Both are pinned in the group below. `_openToShow` keeps the second out; turning the fade back leaves show intent set, as after `a.hide(); a.show()` with no eviction. Without the `isEvicted` condition every test stays green (mutation): a tooltip that is not evicted has `_showIntent == _openToShow` once its reconcile has run, so either branch changes anything only for a `hide()` between a trigger edge and that microtask, where the condition keeps 66960f7's behaviour. A `hide()` during a fade begun by suppression without an eviction is not a dismissal either: the pointer moving back shows it, during the fade and after it alike (measured on 66960f7, pinned in `test/just_tooltip_dismissal_test.dart`). A fade turned back by `controller.show()` after a mid-fade settle keeps `_dismissed`, so the tooltip, shown with no show intent, stays when the pointer leaves — as it does when `show()` comes after the fade on 66960f7; on 66960f7 a nested tooltip crossed during the fade made it hide on leaving instead (measured by #126's lens).
- **Dismissal.** `_shown` (static) lists shown tooltips in show order — a reverse-catch re-tracks — and `_dismissTarget` is the last one not already reversing. `_dismissByUser` marks the tooltip dismissed for each trigger inside (`_markDismissed`), drops `_showIntent`, resets the scheduler and hides. A move inside the child sends no edge and never re-derives, so the dismissal matters only where something else reconciles, such as a nested tooltip releasing it (pinned). `_pending` holds tooltips with show intent not yet on screen; Escape with nothing shown dismisses them. `hideTooltip` does the same for its own tooltip: when it is in `_pending` — a hover or focus show waiting out `waitDuration`, the revival's wait included — it calls `_dismissByUser`, whose scheduler reset cancels the wait (ADR-0010 as amended by #136; maintainer, 2026-11-15). Before #136 it went to `_closeOnRequest`, whose `_hide` has nothing to hide, and the wait showed the tooltip (measured on 4f3db24; pinned in `test/just_tooltip_wait_test.dart`, group *a controller hide while a show waits out waitDuration*, three red there). The cancel is in `hideTooltip`, not in `_closeOnRequest`, which the scheduler's `onClose` shares: the auto-hide left over from an earlier show (a `dismissTooltip`, or a `hide()` on a shown tooltip, does not reset the scheduler) can fire during a new trigger act's wait, and it belongs to the earlier show (implementer's derivation). The wait a revival begins is the exception (ADR-0010 as amended by #143; maintainer, 2026-11-17). `_reconcileShowIntent` sets `_revivalWaiting` when the reconcile that begins the wait is the revival's (`_revivalPending`, read at its top) and carries no act, and the tooltip is not shown. A later act's reconcile clears it, as `_setPending(false)` does, and `_closeOnRequest` takes a close while it holds as `_dismissByUser`, so the left-over auto-hide cancels the wait. Before #143 that auto-hide reached `_closeOnRequest`'s plain `_hide`: by then the tooltip was neither evicted nor revival-pending, and the wait showed it (measured on 4f3db24 and bed5078: `showDuration` 1 s, wait 300 ms, D's `show()` at 400 ms, `d.hide()` at 1100 ms, the auto-hide due at 1300 ms). The `!act` term keeps a wait begun by a reconcile coalesced from a revival and an act an act's (implementer's derivation). Since #159 a revival that `keepsWaiting` turned back clears `_revivalPending`, so the next act's reconcile no longer reads both; before, it did, and `!act` was what kept that wait an act's. Pinned in `test/just_tooltip_wait_test.dart`: *… revival waits out waitDuration, cancels the revival …* is red on bed5078 and with the branch removed; *… after a revival the registry turned back …* is red only with both the `!act` term and the turned-back clear removed; *… a revival and a new trigger act in one reconcile …* (D's zero-length fade ending and the pointer entering before the revival's microtask) is red without the `!act` term; *… a new trigger act during the wait a revival begins …* is red without the clear on an act (a Tab in the wait reaches a reconcile that returns early, since show intent is already set); *… once lost content has hidden the tooltip …* is red without the clear in `_setPending`; and in `test/just_tooltip_tracking_test.dart`, *… the wait the child coming back begins …* is red without the revival term. Read as show intent alone (dropping the `!_isShowing` half of what `_pending` holds), a `hide()` on a shown tooltip dismissed it at once, so a `show()` turning the fade back left it with no show intent and the pointer leaving did not hide it (mutation, pinned). The `HardwareKeyboard` handler is added while `_shown` or `_pending` is non-empty (`_syncKeyHandler`).
- **A dismissal is released only by its trigger moving away** (ADR-0010 as amended by #127; maintainer, 2026-11-15). `_dismissed` is a getter over two holds, each in force only while its trigger is reported inside (maintainer, #127's run): `_pointerHold && _pointerInside`, `_focusHold && _keyboardFocusInside`. `_markDismissed` adds a hold for each trigger inside at the close and keeps the holds already set — overwriting them released, with no movement, a pointer hold an earlier close had left (#127's re-review: tap-closed, `enableHover` off, `controller.show()`, Escape, `enableHover` on under the still pointer showed it; pinned); since `_pointerInside` and `_keyboardFocusInside` are cleared when their trigger is turned off, the facts need no `enableHover`/`enableFocus` term. The pointer's hold is released by the child's `MouseRegion` edges that the pointer's own movement caused (`_pointerMoved`): `onExit`, and `onEnter` too, since a pointer that moves into the child was outside it. Edges `MouseTracker` sends after a frame for the tree changing under a resting pointer release nothing ([a-still-pointer-sends-no-edge](../invariant/a-still-pointer-sends-no-edge.md)): a route's barrier covering or uncovering the child, the region removed and re-created by `enableHover` or `tap` changing, the child laid out from under the pointer and back; the edge after a pop or after `enableHover` is turned back on reports the pointer inside again, and its hold applies again. Where such an edge, a `tap` change or `enableHover` turned off clears the pointer fact, or `enableFocus` turned off clears the focus fact, while a close is fading out, the close is settled first (`_settleFadingClose`, which `_dropShowIntent` uses too), while the trigger still counts — #127's lens measured the first cut letting the first three bring the tooltip back during the fade, the window #117 and #126 named, and the re-review measured the fourth (all pinned). The focus hold is released when `_onFocusChanged` finds focus outside the tooltip, for any cause — focus a route takes or a re-created child loses — since focus can only become the trigger again by a key, which is a real return; `enableFocus` turned back on releases it when focus is no longer inside, since the listener was gone meanwhile (#127's review: otherwise focus that left while it was off kept it, measured). While the tooltip is dismissed, a trigger that comes in holds it too (the reconcile adds its hold), which keeps the rule "until no trigger is inside" for two triggers: dismissed by the pointer, focus arriving, the pointer leaving — still closed while focus stays (pinned both ways). Once the tooltip shows by show intent its holds are cleared, so a hold left by a trigger turned off cannot hide a tooltip the other trigger showed once it is back (pinned). Before #127 the reconcile cleared one `_dismissed` flag whenever no trigger was inside, so a dialog pushed and popped over a tap-closed tooltip under a still pointer, `enableHover` turned off and on, or the child scrolled from under the pointer and back showed it again (measured on 4f3db24 and on the tree with #130 only; pinned in `test/just_tooltip_dismissal_test.dart`, group *a dismissal is released only by its trigger moving away*, nine red on 852a10b). A `tap` change already stayed closed on 4f3db24: `didUpdateWidget` clears the pointer fact, and the new region's `onEnter` after the same frame sets it again before the reconcile's microtask reads it (pinned as a guard). The pointer moving away and back while a dialog covers the child, the pop landing over it, sends no edge either; the tooltip stays dismissed until the pointer leaves and returns once after the pop (maintainer, 2026-11-15, #127's run: chosen over watching the pointer through a global pointer route while covered, and over comparing positions; pinned). A second mouse entering releases a hold the first one left, since the hold is one bool per tooltip, as `_pointerInside` is (#127's review, measured; see Known holes).
- **Two Escape paths, because only one can consume** (measured on Flutter 3.41.9, #92). `KeyEventManager` hands a key to every `HardwareKeyboard` handler *and* to the focus system's `Shortcuts`, whatever the handlers return, so a handler cannot keep a dialog's `DismissIntent` from closing it. `_handleKey` therefore closes a target that does not hold focus itself — the hover case, where the dialog closes too — and leaves one that does in `_deferred`, with a microtask to close it after the press. `_DismissTooltipAction`, the `DismissIntent` action in an `Actions` around the whole tooltip (child and content), is on the focus path and nearer than the route's: it closes `_deferred` and consumes. A nearer enabled action inside the tooltip (a `DropdownMenu`'s) takes the key instead; the microtask then closes the tooltip. Either way one press closes one tooltip: the handler runs first and does one or the other.
- **Forwarding.** With nothing deferred the action hands the intent to the nearest `DismissIntent` action above the tooltip, found by walking `Actions` widgets (no dependency is registered, unlike `Actions.maybeFind`) and called with the focused context when it is a `ContextAction`. A nearer `Actions` for an intent shadows the ancestor's even while disabled (measured), so returning disabled would have kept every dialog around a tooltip from closing on Escape.
- **Covered** (ADR-0011). `_covered` reads `_route.isCurrent` at the moment it is asked; `_RouteStatus`, a child that depends on `ModalRoute.of`, only reports the route so `_updateCovered` can act on a change. On covering, `_syncCovered` drops `_showIntent` and `_pending` and resets the scheduler at once, then hides after the frame, so `_onAnimationStatus` finds no show intent and sets no `_dismissed` — with a zero-length fade the hide ends synchronously, and dropping show intent after it would have marked the tooltip dismissed (pinned by the zero-duration case in `test/just_tooltip_covered_test.dart`). On uncovering it reconciles only when a trigger is inside, since otherwise the reconcile is a no-op on every tooltip of the route. The gate in `wants` matters for a reconcile that runs while covered (a configuration change): without it `_showIntent` turns true, `_show` refuses, and the tooltip never reopens.
- **Clipped away** (ADR-0010 as amended by #130; maintainer, 2026-11-15: the clip-away hide is not a dismissal, as a covered hide is not; a trigger does not show the tooltip while its child is clipped away entirely; Escape or `controller.hide()` meanwhile is not a dismissal). `_childClippedAway` resolves the child against the [Overlay](../../../GLOSSARY.md#visible-rect) as last laid out, and is a gate of `wants` and `_openToShow`, read at the moment it is asked, as `_covered` is; it is evaluated after the other gates, so a reconcile pays for the clip walk whenever a trigger is inside and no gate but eviction holds the tooltip back, shown or not. A reconcile it blocks starts `_watchClippedChild`, a post-frame callback that re-arms itself each frame while a trigger is inside and the tooltip is not shown (a fade-out counts as not shown), then reconciles once the child is visible; `_watchingClippedChild` keeps it to one callback per frame. A reconcile that starts a wait (`waitDuration`, `_pending`) starts the watch too: a child clipped away while the show waits calls the wait off — show intent dropped, `_pending` cleared, the scheduler reset — as covering does, so the timer never shows it at the clip edge, Escape and `controller.hide()` then find nothing pending (Q2), and a `controller.show()` keeps its edge anchor (#130's re-review lens measured all three going the other way when the wait went unwatched; pinned in the group *clipped while a show waits out waitDuration*). [Target tracking](target-tracking.md)'s hide goes through `_hideClippedAway`, which drops show intent through `_dropShowIntent` before `_hide`, so the fade's end infers no close, and a close already fading out (a tap, the auto-hide, a controller) is still settled as one; with a trigger inside it starts the watch too. `_noteTarget` hides a tooltip that show intent holds even when it never saw the child visible, so a reconcile that read the child visible a frame before it was clipped again (a scroll in progress, or the end of `waitDuration`) does not leave it at the clip edge, where `_show` resets `_sawVisibleTarget` and the edge anchor would otherwise hold; `controller.show()` has no show intent and keeps that anchor. `_resolveTarget` resolves a child with a degenerate transform — kept alive off screen by a lazy list — as clipped away ([target-resolution](target-resolution.md)). A first build gated only after the tooltip's own clip-away hide (`_clipHidden`); #130's lens measured it leaving the tooltip at the clip edge in both of those races and, as on b235b85, after a revival, content returning or uncovering while clipped, and #130's review measured the watch multiplying, one more per layout during the fade (71 after a 600 ms `animateTo`). Escape finds no target and no `_pending` entry while it waits, and `hideTooltip` and `_closeOnRequest` find it in neither `_pending` nor `_openToShow`, so neither marks a dismissal (Q2). A hover-shown tooltip whose child scrolls out from under a resting pointer: the clip-away hide runs first, since `MouseTracker`'s update is a post-frame callback `RendererBinding` adds after `drawFrame` (Flutter 3.47.1 `rendering/binding.dart`), so the watch starts and the pointer's exit then ends it; the post-frame `onEnter` when the child scrolls back shows it again, on 4f3db24 too. The covered path also resets the scheduler and drops `_pending`; here the tooltip is shown, so it is never pending, and no timer of the scheduler acts on it in a way a test sees (both lines survived every test as mutations and were left out). Pinned in `test/just_tooltip_tracking_test.dart`, group *a tooltip its clipped-away child hid is not dismissed* (fourteen red on 4f3db24); the gate's mutations redden only through the `onShow` log, since without it the tooltip is drawn at the edge for a frame and then hidden by `_noteTarget`.
- `activate` re-runs `_syncSuppression` and the reconcile after `_readScope`: a reparented tooltip with the pointer still on its child or focus still inside shows again and claims its new ancestors — unless it is evicted and another tooltip holds the place, where it waits for the revival (#116), or it was dismissed.
- **A move keeps the trigger** (#122; implementer's derivation; the focus case below — an Escape-dismissed tooltip moved with focus inside stays closed — shown to the maintainer and accepted, 2026-11-15). `_hideImmediate`, which `deactivate` runs, ends the show and drops show intent through `_dropShowIntent`, and leaves `_pointerInside`, `_keyboardFocusInside` and `_dismissed` as they are. A `GlobalKey` move keeps the child's `MouseRegion` render object — a reparented `RenderObjectElement` inserts the same one, and `MouseTracker` keys its edges on the annotation's identity (`rendering/mouse_tracker.dart`, Flutter 3.47.1) — so a pointer resting on the moved child sends no `onEnter`, and one the child moved away from gets `onExit` after the frame. Before #122 the teardown cleared `_pointerInside` and `_dismissed`: a hover-shown tooltip moved under a resting pointer stayed hidden until the pointer left and returned, and a focus tooltip dismissed with Escape came back after a move with focus inside (both measured on 7b0f3ce). Keeping `_dismissed` follows ADR-0010's "stays closed until its trigger leaves and returns": a move is not the trigger leaving. Settling through `_dropShowIntent` keeps a close fading out when the move lands — a tap, the auto-hide, `controller.hide()` — a dismissal, as the fade's end would have. Pinned in `test/just_tooltip_teardown_test.dart` (group *a tooltip moved by a GlobalKey under a resting pointer*), the keyboard test and the eviction test. Only a trigger inside brings the ended show back: a show the pointer on the body alone holds (the body is not a trigger, ADR-0012) or `controller.show()` started stays hidden after the move, where Flutter's `RawTooltip` keeps its tooltip shown (maintainer's judgement, 2026-11-18, #163; [a-move-ends-only-the-show](../invariant/a-move-ends-only-the-show.md)). Pinned in `test/just_tooltip_teardown_test.dart` (group *an interactive tooltip moved by a GlobalKey with the pointer only on its body*: hover-shown and `controller.show()`, both red without `deactivate`'s `if (_isShowing) _hideImmediate();`).
- Edge handlers only record facts (`_pointerInside`, `_anchorCandidate`, `_regionPosition`) and call `_syncSuppression` synchronously, then `_scheduleReconcile`. The reconcile is coalesced into one microtask because Flutter dispatches every `onExit` then every `onEnter` synchronously for one move.
- One escape hatch: the tooltip body's `onEnter` calls `_flushReconcile` before `onTooltipEnter`, after recording the pointer on the body, so the child's deferred exit is derived with the body holding the tooltip — it arms no bridge (#149) — and has dropped show intent before `_turnsBackFromBody` reads it. Without the flush only the turn-back test *turns back an auto-hide fade, and pauses showDuration* goes red (measured by #149's run; 14 red before #149). After a turn-back it queues the reconcile again (`_scheduleReconcile`, as every edge does), so the turned-back tooltip takes the show intent its triggers give it (below); the flush stays the one synchronous reconcile (ADR-0003).
- **The body turns a fade back as the child would** (ADR-0012 as amended 2026-11-16, #134; maintainer's judgement; the mechanism is the implementer's). The body is not a term of `wants`: the pointer on it never gives show intent. Its `onEnter` asks `_turnsBackFromBody`, and with `turnBack` the scheduler's `onTooltipEnter` requests a show, which turns the fade back through `_show`. The predicate is what the reconcile would decide had the pointer entered the child in the same state: `_fadingOut`, no show intent already set (a transition is what reaches the scheduler; with show intent set — keyboard focus inside through an auto-hide fade, or the show intent `_closeOnRequest` gives back to an evicted tooltip — a child entry changes nothing), `enableHover` on — an explicit term, since keyboard focus alone satisfies the trigger term below, and an eviction fade of an `enableHover: false` tooltip with focus inside was turned back from the body until it was added (measured by #134's lens) — then `_openToShowIfVisibleWith(pointerInside: true, …)`, so a focus hold still in force refuses it and a focus suppressor yields to the pointer, then `!_childClippedAway`, and on an evicted tooltip only when the pointer moved (an act). The pointer hold counts only when the body came under a still pointer, as a child entry by a move releases the hold first. The turned-back tooltip then takes the show intent its triggers give it: the body's `onEnter` queues the reconcile after a turn-back, so it is in the state it would be in had it crossed there from the child with no fade — no show intent (the child's exit dropped it, and the body is not a trigger) unless keyboard focus holds it — and the body's exit then does what it did before: the bridge, the auto-hide restarted, or nothing while focus holds it. Focus can hold a turned-back tooltip only after an eviction fade: elsewhere focus holding it keeps show intent set through the fade, and `_turnsBackFromBody` asks for none. The turn-back is what changes the derivation, since `_show` takes the registry back and `waiting` no longer holds. Before (ada5e3e to 8893217) the turned-back tooltip kept show intent `false` whatever held it, and with focus holding it nothing was left to close it: focus leaving, `enableFocus` turned off, the pointer leaving before focus, `interactive` turned off and a registry change each left it shown for good, its child scrolled out of sight did not hide it (`_noteTarget` hides without show intent only after a layout has seen the child, and a turn-back resets that and lays nothing out), and focus leaving while the pointer rested on the body left it until the pointer left, where after crossing from the child it hid after the bridge (resting on the body was not entering it; since #149 both stay until the pointer leaves) — 14 rows of the matrix below that differed from entering the child (measured on 8893217); and, in a probe of its own, one `showDuration` closed was not marked dismissed, so the next re-derivation (`enableHover` turned off) showed it again with focus never moving (measured on 8893217; pinned in `test/just_tooltip_body_test.dart`, group *a tooltip keyboard focus holds, its eviction fade turned back from the body, …*, each body case red there and its child case green). Running the reconcile synchronously (1bd4910's cut), or on every body entry rather than only after a turn-back, changes no test and no matrix row (mutations): after the flush nothing but the turn-back can change what it derives. The microtask keeps the flush the one synchronous reconcile ADR-0003 records. **The closers matrix** (the cls run of #134, 2026-11-16) crossed every fade the body can turn back — the bridge, the auto-hide, `controller.hide()`, Escape, an eviction by a controller or under a hovering pointer, nesting suppression by the pointer or by focus — with focus in the tooltip or not, the pointer entering the body or the child, resting afterwards on the body, on the child or away, and fifteen closers: the pointer leaving, focus leaving, each in either order, `enableHover`, `enableFocus` and `interactive` turned off, Escape, `controller.hide()`, an eviction and the revival after it, content lost and back, covered and uncovered, the child clipped away and back, a registry change, a `GlobalKey` move, and `showDuration` set — 1350 cases, 20 ms steps, body against child on every row; after the fix none differ. Only an entry asks: a revival during an eviction fade with the pointer resting on the body does not turn the tooltip back, where resting on the child it does (maintainer's call, 2026-11-16, ADR-0012 amendment). Each case is pinned beside the same case entering the child in `test/just_tooltip_body_test.dart`, which measured child and body alike on this change: the bridge running out, the auto-hide, `controller.hide()`, Escape with the pointer away, an eviction (the registry taken back), the body or child coming under a still pointer during a `controller.hide()` fade (turned back) and during an eviction fade (not), Escape with focus inside, and an auto-hide fade focus still holds (neither turned back). Before, only the child turned a fade back: the bridge running out, the pointer reaching the body mid-fade → gone, `[show, hide]` (measured on fd0a9be). `_fadingOut` keeps a body still in the tree after the show ended from opening the tooltip again: `_endShow` hides the overlay, and the body leaves the render tree only with the next frame, so a pointer entering it in between reaches `onEnter` (measured in #134's check: a zero-length fade, `controller.hide()`, the pointer onto the body before the next pump — reopened without the guard). The same window is why `_pointerOnBody` follows the region's lifetime rather than the show's ([visibility-scheduling](visibility-scheduling.md)).
- A transition to `false` caused by suppression or lost content is not a hover exit: `_scheduler.reset()` + `_hide()`, bypassing `onChildExit`'s `showDuration` policy.
- `onExit` clears `_anchorCandidate` so a later programmatic show cannot anchor at a cursor that has gone.
- `didUpdateWidget` clears `_pointerInside` and `_anchorCandidate` when `enableHover` turns off (#124, #138). Turning it off removes the child's `MouseRegion`, and a detached region gets no `onExit` (`RenderMouseRegion.detach` clears `validForMouseTracker`, which `MouseTracker` checks before each exit; Flutter 3.47.1), so the fact had no one left to correct it. Before #124 it outlived the region: a nested tooltip turned off under a resting pointer kept suppressing its ancestors, and a tooltip turned back on after the pointer had left showed with the pointer elsewhere (both measured on 7b0f3ce). Turned back on under the pointer, the new region gets `onEnter` after the frame, which sets the fact and the position again and is not an act. Before #138 the position was left as it was, so a pointer-anchored `controller.show()` after the pointer left anchored where the cursor had been when hover went off (measured on 9f7e720: x=80 against the child's centre 350). The clear runs on the on-to-off edge, not on every update while hover is off. For `_pointerInside` the two forms agree, since nothing sets it while the region is gone; but the position can also hold a tap's down point, and a rebuild that changes nothing must not move where a later show anchors (pinned by 'a tap a nested tooltip took anchors a later programmatic show at the tap, across a rebuild and the nested show ending'; implementer's derivation). Since #141 a tap's position also ends with the show it served ([target-resolution](target-resolution.md)).
- A non-interactive body sits in `IgnorePointer(ignoring: !interactive)`, so it never takes the pointer from its child. Placement can lay the body over the child — one too large for either side is clamped onto it — and an opaque body there made the child report `onExit`, the tooltip hide at once, the child uncover and the tooltip show again: shown on every other 50 ms sample in a 390-wide view with a 300-wide `left` body (#65). An interactive body keeps taking the pointer, because the bridge it cancels on `onEnter` is what keeps it shown. Flutter's `Tooltip` makes the same split (`ignorePointer ?? message != null`, Flutter 3.47.1 `material/tooltip.dart`). Cost: a tap on a non-interactive body reaches the widget beneath it.

Input: pointer, focus and key events; six retained bools and one offset per tooltip, static sets as large as the tooltips shown or pending at once, and per registry a set as large as the tooltips it has evicted.

## Reference behaviour

- Flutter 3.41.9 `widgets/raw_tooltip.dart` — `RawTooltipState._handleMouseEnter` / `_handleMouseExit` keep a set of hovering devices (`_activeHoveringPointerDevices`) rather than a single edge, and rely on the documented "all `onExit` before any `onEnter`" order in a comment. This package does not rely on that order; it coalesces instead (ADR-0003 calls the order undocumented).
- Flutter 3.41.9 `widgets/raw_tooltip.dart`, `material/tooltip.dart` — no focus trigger and no Escape handling; this territory goes past them on purpose (ADR-0010). `services/hardware_keyboard.dart` `KeyEventManager.handleKeyData` — both the `HardwareKeyboard` handlers and `keyMessageHandler` run for every key; `widgets/actions.dart` `Actions.maybeInvoke` — a suitable action found disabled stops the search; `widgets/focus_manager.dart` — `FocusManager` notifies its listeners when `primaryFocus` changes, and `_HighlightModeManager` switches to touch only for touch and stylus pointers.

## Blast radius

- [visibility-scheduling](visibility-scheduling.md) — it assumes it is fed transitions in "child, then tooltip" order; the flush is what keeps that true.
- [nesting-suppression](nesting-suppression.md) — `_suppressed` is a term of the formula, and the claim must stay synchronous while the reconcile is deferred.
- [content](content.md) — `_hasContent` is a term; content loss takes the immediate-hide branch.
- [target-resolution](target-resolution.md) — `_anchorCandidate` recorded here is what a pointer anchor freezes.
- [tap-trigger](tap-trigger.md) — the tap path writes `_anchorCandidate` too and bypasses show intent entirely; a tap still opens a dismissed tooltip.
- [visibility-lifecycle](visibility-lifecycle.md) — `_show` tracks the tooltip in `_shown`; `_endShow`, reached from the dismissed animation status and from `_hideImmediate`, untracks it and leaves the registry, which revives the evicted tooltips.
- [tooltip-registry](tooltip-registry.md) — the registry records the evicted tooltips and decides when they are revived; `_shown` keeps a second, app-wide record of what is shown.
- [semantic-tooltip](semantic-tooltip.md) — nothing may be put around the child that adds a semantics node, or the child's node splits.

## Known holes / open

- The closers matrix's two findings outside the body turn-back are closed: `enableHover` turned off while the pointer rests on the body by #150 (the body's exit after an entry made with hover on hides at once), and `showDuration` set on a tooltip shown with no countdown running by #151 (the change restarts the countdown at once; cleared, a trigger exit the countdown held asks for its hide) ([visibility-scheduling](visibility-scheduling.md), ADR-0012).
- `enableHover` turned on during a fade while the pointer rests on the body does not turn the fade back, where resting on the child it does: the child's new `MouseRegion` gets an enter under the still pointer, and the body's region was there all along (measured by the closers run's lens on fd0a9be, 8893217 and 1bd4910 alike; the tooltip still closes). Same shape as "only on entry"; the maintainer was shown the revival case, not this one.
- Multi-pointer: one `_pointerInside` bool per tooltip, where `RawTooltip` tracks a device set, and one `_pointerHold` with it. Two mice are not modelled; nothing records whether that is deliberate. A second mouse entering the child releases a dismissal the first one's rest holds (#127's review, measured).
- Tests that inspect state between `onEnter` and the microtask see the stale value (ADR-0003, consequences) — any new test here must pump.
- Whether the key goes on to the platform (`_DismissTooltipAction.consumesKey`, and its `isEnabled` claiming the deferred press when no action encloses the tooltip) is invisible to a widget test; both mutations stay green.
- The state cleanup at `dismissed` (`_showIntent` still set) changes nothing a widget test sees — the next show still needs the trigger to return — but without it the tooltip stays in `_pending` and the keyboard handler stays installed; its mutation stays green (measured again with #106's tests, which do not see it either).
- Forwarding calls the enclosing action directly, so an ancestor `Actions(dispatcher: …)` does not see an Escape that passes through a tooltip (read, not run).
- An evicted tooltip whose child is scrolled, resized or laid out under a resting pointer waits for the revival: the edge comes after a frame and is not a new act (implementer's derivation, #116; the maintainer was not shown this case). A wheel scroll is the user's act but moves no pointer.
- When several evicted tooltips are revived together, the order they were evicted in decides which one ends up shown: hover-held A and focus-held F both evicted, D hides → F shows, and A is evicted again (measured by the #113 lens). Nothing records which should win; ADR-0010's "the pointer wins" covers nesting only.
- With the auto-hide after the eviction's fade counted as a close (ADR-0010, #129 derivation 1), whether the tooltip comes back depends on whether the tooltip that evicted it outlasted the rest of its `showDuration`, a timer the user does not see.
- A tooltip a tap closed whose `message` is set to `null` and back comes back, where `''` and back keeps it closed (measured on 4f3db24 and after #127). Cause, traced in #127's run: with no `tooltipBuilder`, `message: null` fails `JustTooltip`'s constructor assert in debug, the error widget replaces the subtree, and a new State is built when the message returns; the new tooltip has no dismissal to keep.
- Several views share `_shown` and one keyboard handler, so an Escape typed in one view closes a hovered tooltip in another (ADR-0010, accepted; read, not run).
